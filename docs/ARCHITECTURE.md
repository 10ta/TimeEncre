## 数据格式

全部是 JSON。时间为带时区的 ISO 8601，id 为 UUIDv7，颜色为 `#rrggbb`，时长不存储、由区间计算。
每个文件都有 `schemaVersion`，读取时经 `src/schema/index.ts` 的迁移链升级到当前版本；
遇到比程序新的版本会拒绝写入。结构定义见 `src/schema/v1.ts`。

## 数据仓库中的布局

```text
TimeEncre/
  profile.json            活动、标签、目标、设置
  records/2026-10.json    按记录开始月份分文件
  keep.json               Keep 的清单与条目（用过 Keep 才会出现）
  daily.json              例程与每日评分（用过才会出现）
```

`daily.json` 是后加的独立文件：旧版本客户端只读写自己认识的文件，所以不会删掉它；例程和评分按条目“较新者胜出”合并，评分的 id 就是日期 `YYYY-MM-DD`。

分文件用的月份取记录第一段开始时间 ISO 字符串里写的年月（即写入时那个时区的日历月），
不随查看设备的时区变化，所以不同时区的设备不会把同一条记录来回搬到不同文件。

## 同步怎么工作

拉取自上次同步以来远端变化过的文件，按每条数据的 `updatedAt` 合并（较新者胜出，删除以墓碑形式传播），
再把与远端不同的本地文件打成一个提交推送。远端在此期间被其他设备或其他 app 更新时（非快进），自动重新合并并重试。
数据文件序列化是确定性的，所以没有改动就不会产生提交，GitHub 上的 diff 也可读。
计时记录额外有一条规则：某一段的“结束”只进不退。一台设备停止了计时，另一台设备还停留在“进行中”时又改了这条记录（比如加了备注），
合并后仍然是已停止（结束时间取停止的那一台），备注等其他改动照常保留，两台设备结果一致。

- 一次同步：读分支头 → 读提交和递归目录树 → 只下载 blob SHA 和上次同步时不同的文件 → 按 `updatedAt` 合并进本地 → 把与远端不同的本地文件用 Git Data API 打成**一个**提交 → `PATCH` 分支引用（`force: false`）。
- 远端在此期间被更新时 GitHub 返回 422，引擎重新拉取合并后重试，最多 4 次。
- 自动同步的时机：启动时、本地改动约一分钟后、页面切到后台时、回到前台且超过 5 分钟没有同步时。
- 待同步计数（顶部徽标）在每次写库后重新生成全部文件并比较 SHA；月份文件的文本有缓存，数据没变的月份不重新序列化。
- 只读写数据目录（默认 `TimeEncre/`）下的 `profile.json`、`keep.json`、`records/*.json`，同一仓库里其他 app 的文件原样保留。

## 统计口径

- 时长都按所选范围 `[from, to)` 裁剪，进行中的记录算到现在。
- 按活动 / 标签汇总时，同时进行的两条记录各算各的；“未记录”和自定义指标按并集算，同时进行的只算一次。
- “未记录”= 第一条记录之后、到现在为止，没有被任何记录覆盖的空档之和。**短于 1 分钟的接缝不算**（`src/lib/gaps.ts` 的 `GAP_MIN_MS`），和历史页列出的空档是同一口径，所以统计页的数字和历史页“全选未记录”能对上。

## 目标的四种类型

目标仍是 `profile.json` 里的 `goals`，新增的都是可选字段（`looseObject`，旧版本会原样保留）；计算集中在 `src/lib/goals.ts` 的 `evalGoal`。

| `kind` | 额外字段 | 一个周期怎么判 |
|---|---|---|
| `duration`（缺省） | — | 周期内累计时长对比 `targetMinutes`，“至少 / 至多” |
| `days` | `minDays` | 周期（周 / 月）里有几天达到 `targetMinutes`，至少 `minDays` 天 |
| `clock` | `clockEdge`、`clockMin` | 每天一次。`start`：开始时间在当天 12:00 到次日 12:00 之间、最长的那条记录，开始不晚于 `clockMin`（凌晨 0:30 才睡算前一晚）；`end`：结束落在当天、最长的那条，结束不晚于 `clockMin` |
| `window` | `windowFrom`、`windowTo` | 只算每天这个时段里的时长（`windowTo ≤ windowFrom` 表示跨午夜），再按“至少 / 至多”判 |

`clock` 型不用时长，但旧版本要求 `targetMinutes > 0`，所以保存为 1。

## 提醒规则

规则是纯函数 `src/lib/nudges.ts` 的 `dueNudges`，由 `Nudges` 组件在页面打开时每 30 秒调用一次（后台标签页里浏览器可能放慢到每分钟一次）。每条提醒有一个 key，提醒过的 key 记在本机 `localStorage`，保留 3 天，同一件事不会重复提醒。

- 上限：“至多”型的 `duration` / `window` 目标，有匹配的记录**正在计时**时，本期到 80% 提醒一次，超出再提醒一次。
- 连续计时：某个活动正在进行的那一段每满 N 分钟提醒一次（`settings.nudges.long`）。
- 忘记计时：没有任何进行中的计时，距离最后一次结束每满 `idleMin` 分钟提醒，最多连着三次。
- 例程开始：例程开始后 15 分钟内，那个活动没在计时就提醒一次。

## 周复盘怎么算

`src/lib/review.ts` 的 `weeklyReview`，只在统计页的周视图显示：

- 要点：各目标本周的达成数；日均变化最大的三个活动（差 15 分钟以上）；未记录；作息；例程的计划 vs 实际（计划时段里实际在做同一活动的时长，同时进行的只算一次）；评分平均。
- 关联（近 8 周、只看已经过完的日子）：把日子分两组——评分 4–5 vs 其他；前一晚睡眠不短于中位数 vs 短于——比较每个活动的日均，每组至少 4 天、差 20 分钟以上才列出，最多 3 条。
- 建议（最多 3 条，按顺序）：“至多”目标本周超了 3 天以上且 40% 以上的时间集中在某 3 小时 → 给那个时段设上限；“至少”目标达成不到一半且没有对应例程 → 在最常做这件事的那个小时加例程；入睡波动 ≥ 45 分钟且没有就寝目标 → 设就寝目标；例程计划 ≥ 2 小时但完成不到一半 → 调整；未记录 ≥ 2 小时 → 去补。

## Pomo 的状态

状态按时间戳计算并保存在本机（不同步）。页面在后台或关闭期间到点，回来时按准确的结束时间结算。
所有 Pomo 操作串行执行（支持 Web Locks 的浏览器上跨标签页也互斥），不会因为多处同时结算而重复建记录。
如果发现有“🍅 番茄钟”记录在计时却没关联到当前的 Pomo（旧版本留下的、或来自另一台设备），Pomo 页会提示，可一键接管或停止。
